# ローカルLLMでスクリプト作成＋ログ解析をするための機材選定

オフライン環境で Linux/Windows のスクリプトを調査〜作成し、ログ解析もしたい。
どのモデル・どの機材が必要かを調べた記録。

## ① 何を知りたかったか

- ネット環境なしで、スクリプト作成とログ解析ができるモデルのライン
- 大きいモデルほど正確なのか
- 現場に持ち出すならどの機材か
- Mac でスクリプトを作って、Linux/Windows で動くのか

## ② 調べて分かったこと

### 結論のライン：30Bクラスが実用ライン

| VRAM/メモリ | 現実解 | できること |
|---|---|---|
| 8〜12GB | Qwen2.5-Coder 7B | 単発スクリプト生成。自律エージェントは精度不足 |
| 16GB | Qwen2.5-Coder 14B / Phi-4 14B | 単体作業なら十分 |
| **24GB〜** | **Qwen3-Coder 30B-A3B (Q4)** | **調査〜作成〜デバッグまで安定** |

エージェントは **Aider**（ターミナル・成熟している）か
**Cline / Roo Code**（VS Code・差分レビューできるので初学者に安全）。
基盤は Ollama か LM Studio。

### 学び1：大きいモデル＝正確、ではない

**同じ予算なら、大きいモデルを無理に圧縮するより、新世代の30Bクラスを
高品質量子化で動かす方が正確。**

理由は3つ：

1. **世代とコード特化がパラメータ数より効く**
   24GB環境で7モデルを実測した比較では、30〜35B級は品質がほぼ横並びで、
   差がついたのは速度と安定性だった
2. **大きいモデルは強い量子化が必要になり、逆に劣化する**
   120BモデルをIQ3_XXSで動かしたテストで正解率6.2%、完了に27分という実例
3. **エージェント用途では速度も精度の一部**
   「書く→実行→エラーを読む→直す」を何十回も回すので、
   1回3倍遅いと同じ時間で試せる修正回数が1/3になる

### 学び2：ボトルネックは速度ではなく容量

Ryzen AI MAX 32GB での失敗例：35B-A3B（24.3GiB）がOOMで落ち、
ブラウザを閉じてようやく起動できた。

**Aider/Clineはファイル内容やログを大量にプロンプトへ詰め込むため、
KVキャッシュが膨らむ。チャットなら足りてもエージェントを回すと後半で尽きる。**

### 学び3：一台で全部やる場合のメモリ内訳

| 用途 | 消費 |
|---|---|
| macOS＋ブラウザ・エディタ | 8〜10GB |
| ローカルLLM（30B-A3B Q4） | 18〜20GB |
| コンテナ（Docker/Colima） | 4〜8GB |
| KVキャッシュ（長いログ） | 2〜6GB |
| **合計** | **32〜44GB** |

→ 32GBだと天井に張り付き、コンテナ起動でスワップする。**48GBが実用点。**

※ 実際、Colima ON で 21 tok/s、OFF で 30.9 tok/s という実測を別途取っている。
　 コンテナとLLMはメモリを奪い合う。

### 学び4：Mac vs Ryzen（現場持ち出し前提）

| | Mac | Ryzen AI MAX |
|---|---|---|
| 消費電力 | M4 mini 実測30W前後。バッテリー持ちに直結 | 推論時 数十〜100W級 |
| 環境構築 | MLX/Ollamaで詰まりにくい | ROCm/カーネル/ファームウェアの地雷 |
| 同価格帯のメモリ量 | 少ない（高価） | 多い（128GB機がミニPC価格） |
| **Windows検証** | **不可** | **可能** |

**現場は「その場で直せない」場所なので、安定性の価値が大きい。**

## ③ どう判断したか

### 用途に対する結論

貼り付け方式（ログを持ち込んで解析→スクリプト生成）なら
エージェントの自律ループが不要なので **MacBook Pro 32〜48GB で十分**。

一台で解析もコンテナ検証もするなら **M4 Pro / 48GB / SSD 1TB**。

- **M4 Pro を選ぶ理由**：トークン生成速度はメモリ帯域でほぼ決まる。
  M4無印 約120GB/s に対し M4 Pro 約273GB/s で2倍以上の差。
  さらに無印は最大32GBまでしか選べない
- **SSD 1TB の理由**：モデル1本20GB前後＋コンテナイメージ数十GB。後から交換不可

### 運用のコツ

常時30Bを起動しっぱなしにしない。
**「普段は9Bで会話、重い解析のときだけ30Bを起動」** で48GBでも余裕が出る。
Ollamaは一定時間で自動的にモデルをメモリから降ろすので自然にできる。

### ログ解析の定石

Qwen3-Coderは26万トークンの長文脈対応だが、
**巨大ログを丸ごと読ませず、grep等で絞ってから要約させる。**
コンテキストが長いほど速度と精度が落ちるため。

## ⚠️ 落とし穴：Macで作ったスクリプトが動かない理由

**Mac自体は問題ない。LLMが出すのは単なるテキスト。**
危険なのは **Macで動作確認してしまうこと**。
macOSのコマンドはBSD系で、Linux標準のGNU系と挙動が違う
（`sed -i` の書き方、`date` のオプション等）。

### 頻出エラー上位

1. **改行コード（最頻出）**
   - Linux側：CRLFのシェルスクリプトは `bad interpreter: /bin/bash^M` で即死
   - 対策：LF指定、または `dos2unix`
2. **文字コード**
   - Windows既定はShift-JIS(CP932)、Linux/MacはUTF-8
   - 対策：PowerShellなら `Out-File -Encoding UTF8` を明示させる
3. **CPUアーキテクチャ**
   - MacはARM、サーバは通常x86_64。シェルスクリプトなら問題ないが
     コンパイル済みバイナリで差が出る

### コンテナ検証で埋まらない穴

- **systemdが動かない**：`systemctl` を含む処理は標準コンテナで検証できない → UTM等のVMが必要
- **Windows検証は不可能**：Windowsコンテナの実行にはWindowsホストが必須。
  LinuxコンテナでPowerShell 7は動くが、Windows標準は5.1。
  レジストリ・WMI・イベントログも使えない = **動作確認になっていない**

→ Windows向けは「読み取り専用スクリプトに限定」するか、検証用Windows機を別途確保する

## 教訓

- **「大は小を兼ねる」はローカルLLMでは成立しない。** 量子化による劣化があるため
- **投資先は「より大きいモデル」より「30BクラスをVRAMに全部載せて高速に回せる環境」**
- 実践記事の警告：**Gitなしでエージェント・コーディングをやるのは自殺行為**
  （LLMは作るのも消すのも得意すぎる）
- 「作れたのに使えない」を防ぐため、**生成物を現場へ持ち込む経路（USB可否等）も
  事前に決めておく**
