# アインシュタインの思考実験が、開発中アプリの「隠れたバグ」を言い当てた

小学生向けに物理を説明したいという、開発と無関係な好奇心から入った寄り道が、
気づいたら開発の一番大事なところに届いていた記録。

## ① きっかけは「子どもに説明したい」だった

入り口は開発ですらなかった。
アインシュタインの思考実験を、小学生にも分かるように説明できないか——
ただそれだけの興味で調べ始めた。

- 光を追いかけたらどう見えるか
- 走る電車の前後に落ちた雷は、誰にとって「同時」なのか
- 落ちるエレベーターの中では重力と無重力を区別できるのか

## ② 物理側で理解したこと

### 「同時」は見る人によって違う（同時性の相対性）

長い電車の前と後ろに雷が落ちる。

- 線路わきに立つ人 → 両方の雷は「同時」に見える
- 電車の真ん中に乗る人 → 前に進んでいる分、前の雷の光に早く出会う
  → 「前の雷が先」に見える

**「同時に起きた」かどうかは、見る人の動きによって変わる。
時間は、みんな共通の1つではなかった。**

### 光速一定を認めると、時間と長さが伸び縮みする

速さ ＝ 距離 ÷ 時間。
光の速さが誰にとっても同じなのに、見る人の動きはバラバラ。
つじつまを合わせるには、**「距離」と「時間」のほうが伸び縮みするしかない。**

「光の時計」の思考実験がこれを一番きれいに見せる：

- 時計を**持っている人**から見ると、光はまっすぐ上下（最短コース）
- 時計が**横を通り過ぎるのを見る人**から見ると、光は斜めのジグザグ（長い道）

光の速さは両者で同じ → **長い道のり ÷ 同じ速さ ＝ よけいに時間がかかる**
→ 動いている時計は、外から見るとゆっくりチクタクする

### 思考実験という方法そのもの

現実には絶対にできない状況を頭の中だけで完璧に再現し、
すでに分かっている法則をその極限状況に当てはめて、矛盾や新しい原理を見つける。

1. すでに正しいと分かっている法則を用意する
2. その法則を**現実には作れない極端な状況**に放り込む
3. 出てきた矛盾から新しい原理を導く

**実験のプロセスは想像でも、結論は現実で検証できた**（1919年の日食観測）。
だから単なる空想で終わらなかった。

## ③ 数日後、これが開発に刺さった

電車アプリの設計を進める中で、突然つながった。

> **「同時」が観測者によって違うなら、
> このアプリの"今"も、立場によって違うのでは？**

### 発見：このアプリには「今」が4つある

```
今①: データが作られた今      → ODPTの dc:date
今②: データの賞味期限        → dct:valid
今③: 列車の本当の今（推測）  → 今① + 経過時間 × 速度
今④: ユーザーが画面を見た今  → アプリ側の現在時刻
```

### 何が問題だったか

**「今① ＝ 今④」と暗黙に決めつけていた。**

受け取った位置データを「今の位置」だと思い込んでいた。
でも実際は、データが届くまでに時間差（通信＋取得間隔）があり、
**画面を見た頃には電車はもう先に進んでいる。**

> **「リアルタイムデータ」と呼ばれるものの多くは、実は少しだけ過去。
> 届いた瞬間にはもう古い。**

### 修正した設計

受け取った位置を"今"だと思わず、**経過時間ぶんだけ電車を前に進めてから判断する。**
（船や飛行機で使う「推測航法 / dead reckoning」と同じ考え方）

```python
elapsed = now() - parse(data["dc:date"])      # データが届くまでの時間差
if elapsed > valid_span:
    state = "STALE"                            # 賞味期限切れ → 判断材料にしない
estimated_now = last_position + elapsed * avg_speed  # 列車の"本当の今"に補正
```

### もう一段の応用：「変わらない量」を軸にする

アインシュタインは「**誰から見ても変わらない量（光速）を軸にすれば矛盾が消える**」
と気づいた。このアプリにとっての"変わらない量"は何か？

鉄道会社目線の「◯分遅れ」ではなく、**ユーザー目線の「間に合うか」**だった。

```
入力（鉄道の基準系）  : 遅延 = 180秒
   ↓ ユーザーの基準系へ変換
出力（ユーザーの基準系）: 「8:14に家を出れば間に合います（余裕6分）」
```

## ④ なぜこの寄り道に価値があったか

**エンジニアなら最初から技術書を読むところを、物理の読み物から入った。**

ここまで「間隔」「団子」「相対比較」と設計を固めてきたが、
どれも **「データの"今"は正しい」という前提**に立っていた。
その前提自体を疑えたのは、技術の外から来た視点だったから。

## 教訓

- **「リアルタイム」を疑う。** 届いたデータは少し過去。
  この時間差を設計に組み込む。**電車に限らず、あらゆるリアルタイム系アプリに効く**
- **物理や哲学のような一見関係ない知識が、設計のバグを言い当てることがある**
- **暗黙の前提こそが最大のバグの温床。**
  「今①＝今④」は、誰も明示的に決めていないのに全員が信じていた
- **「誰から見ても変わらない量」を探すと、矛盾が消える。**
  基準系を変えて出力する（鉄道の"遅延分数" → ユーザーの"間に合うか"）
- **思考実験の型そのものが応用できる。**
  現実には試せない極端な状況を頭の中で作り、矛盾を探す
