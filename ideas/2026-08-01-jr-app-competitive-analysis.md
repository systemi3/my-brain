# JR公式アプリの競合調査：混雑データの正体と、勝てる場所

電車遅延アドバイザーの開発中、JR東日本公式アプリを調べて
「どこで勝負すべきか」を確定させた記録。

## ① 何を知りたかったか

- JR公式アプリは何を提供しているか。自分のアプリと何が違うか
- あの「列車ごとの混雑」はどうやって出しているのか。個人でも作れるのか
- 首都圏全路線に広げることは可能か

## ② 調べて分かったこと

### 公式アプリとの決定的な違いは「層」だった

| 観点 | JR公式 | 電車遅延アドバイザー |
|---|---|---|
| 提供するもの | 生データの可視化 | **判断・助言** |
| 「あと何分」 | ユーザーが地図を見て**自分で目測** | アプリが**計算して答える** |
| 遅延時 | 遅延の事実を通知 | 「待つべきか・別ルートか」を提案 |
| データ源 | 社内システム | ODPT API（公開データ） |

**競合ではなく、公式アプリの一段上（判断層）を作っている。**

公式アプリのレビューに「山手線全体を見渡して、間隔調整が起きるか自分で予測していた」
という声があった。つまり **ユーザーは今、頭の中で予測作業をしている。**

> **公式が出す走行位置は「材料」であって、「料理（判断）」は提供されていない。**

### 混雑データの正体：車両の「重さ」だった

乗客が乗ると車体が沈む
→ 空気ばねの圧力変化を**応荷重装置**（本来はブレーキの効き調整用センサー）が検知
→ 東京圏輸送管理システム（ATOS）が収集
→ 列車ごとの混雑度を5段階で表示

**混雑専用センサーを新設したのではなく、既存の車両データの転用。**

場所ごとに測り方が違うのも発見だった：

| 場所 | 方式 |
|---|---|
| 列車内 | 車重方式（ATOS対象の首都圏主要線区のみ。他社車両・209系/205系は対象外） |
| 駅構内 | 構内カメラ映像にプライバシー加工 → 約1分周期の静止画 |
| 改札口 | 改札機の通過データ（Suicaのタッチがそのままセンサー） |

※東京メトロは相互直通で他社車両の車重が取れないため、
　デプスカメラ＋AIで車内を直接計測する方式を採用。

### ⚠️ 「リアルタイム」に見えて実は約5分前

公式FAQも「約5分前の混雑状況が5段階で表示」と明言している。
**完璧なリアルタイムを目指さず、5分遅れでも十分価値がある。**

### ODPTで取れるデータと、その限界

JR東日本のデータは3種類（GTFS / GTFS-RT形式）：

1. **運行情報** — 「山手線は大雨のため見合わせ」レベル
2. **時刻表更新情報** — 15:16発が3分遅れて15:19発、といった列車・駅ごとの遅延
3. **位置情報** — 各列車の現在走行位置。**混雑状況は含まれない**

対象範囲も限定的：東京・神奈川・埼玉周辺の一部在来線のみ。新幹線は含まず。
常磐線は羽鳥以南、高崎線は神保原以南、青梅線は立川-青梅間のみ。

### 首都圏データは3階層に分かれている

| 層 | 事業者 | 提供内容 |
|---|---|---|
| 第1層 | 東京メトロ、東京都交通局 | **常時・リアルタイムまで公開** |
| 第2層 | JR東日本 | **チャレンジ期間限定**。終了後の継続は保証なし |
| 第3層 | 一部私鉄 | 静的データ＋運行情報のみ（在線位置なし） |

**作れるかどうかはコード力ではなく、データの供給側で決まる。**

## ③ どう判断したか

### 判断1：混雑では公式に勝てない → 遅延判断に全振り

**混雑データは「物理インフラの独占」なので個人では複製不可能。**
車重センサーもATOSも持てない。→ 迷わず遅延判断に集中できる。

**諦めることを確定させると、集中できる。**

### 判断2：でも設計思想は盗める

JRの本質は **「既存データの転用」と「複数ソースの組み合わせ（実績×当日データ）」。**

同じことができる：

```
ODPTの遅延データ（当日） × 自分で蓄積した過去の遅延履歴（実績）
→ 「この路線、月曜朝の遅延は長引きがち」という
   公式が出していない予測が作れる
```

※天翔ポータルのRAG構想（過去インシデントから予測）と完全に同じパターン。

### 判断3：全路線同じ機能を目指さない（グレースフルデグラデーション）

- 第1層の路線 → 「次の電車まであと4分。3分遅延中」（フル機能）
- 第2層の路線 → 同上。データ供給停止時は自動で第3層表示に落ちる
- 第3層の路線 → 「この路線は現在遅延情報のみ。平常運転です」

**初学者は「全路線同じ機能」を目指してデータの薄い路線で挫折しがち。**
プロの世界では「取れるデータの範囲で最大の価値を出す」のが標準。
JR公式アプリ自体が「209系・205系や他社車両では混雑を出さない」と正直に割り切っていた。

### 判断4：2路線に絞る（都営浅草線 ＋ 京浜東北線）

性質の違う2路線が、偶然「理想的な組み合わせ」になっていた。

| 路線 | 位置づけ | 意味 |
|---|---|---|
| 都営浅草線 | 第1層・常時公開 | **永久に動き続ける成果**が作れる |
| 京浜東北線 | 第2層・期限付き | データ豊富で**見栄えする成果** |

**実装の順番と理由：**

1. **浅草線だけで完成させる** — 常時データなので、作ったものは永久に動く
2. **京浜東北線を追加** — データソースを抽象化してあれば差分実装で済む
   （期限付きデータに最初から依存すると、期限切れ＝成果消滅）
3. **2路線あるからこそできる価値を足す**
   → 例：「京浜東北が5分遅延中なので、浅草線側で1本待つのが得」

### 最大の見せ場：事業者横断アドバイス

**公式アプリは自社データしか扱えないが、
オープンデータを使う個人開発者は会社の壁を自由に越えられる。**

これがODPTを使う個人の唯一かつ最強のアドバンテージ。

## ④ 実装上の注意（着手初日に検証すべきこと）

- **浅草線は京急・京成との直通運転が多い。** 他社車両由来のデータがどこまで取れるか
  （JR公式ですら「他社車両は混雑表示対象外」だった。同じ構造の問題が位置情報でも起こり得る）
- **京浜東北線がチャレンジ2026の対象に含まれるか**、登録後に実データで確認
- **データ層を抽象化しておく**（例：`TrainDataSource` クラスで切替可能に）
  → 常時公開データへの差し替えが1ファイルの修正で済む
  → 天翔ポータルでLLM呼び出し先を環境変数で切り替える設計と同じ発想

## 教訓

- **「作りたい機能」より先に「取れるデータ」を確認する。**
  API開発の鉄則は「データの在庫確認が先」
- **競合調査は最新の実物を見る。** 機能追加は頻繁で、知識は古くなる
- **勝てない場所を確定させると、勝てる場所に集中できる。**
  混雑を諦めたから遅延判断に全振りできた
- **完璧を目指さない割り切りは、プロもやっている。**
  公式ですら「約5分前」「一部車両は対象外」と正直に割り切っている
