# カフェ空席予測サービス：設計思想の転用と、データの壁

「スタバの空席を予測するサービスは作れないか」という思いつきを、
実際に調査・設計してみた記録。実装には進んでいないが、引き出しに置く価値がある検討。

## ① 何をしたかったか

カフェ（スタバ等）の席の空き具合を予測するサービスを作りたい。
まず「同じサービスが既に存在するか」を調べた。

**なぜ最初に競合を調べたか：**
個人開発で一番怖いのは「半年かけて作ったら大企業が同じものを無料で出していた」パターン。
先に競合を知れば、最初から「彼らがやらない一点」に絞って作れる。

## ② 調べて分かったこと

### 既存サービスは3タイプ

| タイプ | 例 | 仕組み | 弱点 |
|---|---|---|---|
| センサー型 | VACAN | 店舗にセンサー/カメラを設置しリアルタイム表示 | センサー設置店のみ＝対象が少ない |
| クラウドソース型 | KUSEKI | ユーザー同士で混雑状況をシェア | 投稿がないと表示されない（過疎問題） |
| 統計推定型 | Googleマップ「混雑する時間帯」 | 過去のスマホ位置情報から推定 | 「行くべき店」の判断はしない |

### 最大の壁は、電車アプリと全く同じ構造だった

```
電車アプリの壁：
  リアルタイム混雑データ → ライセンス制限で使えない
  → 解決策：大都市交通センサス（統計）＋ 相対比較

カフェアプリの壁：
  リアルタイム空席データ → 個人は店内にセンサーを置けない
  → 解決策：同じ。統計（時間帯・曜日）＋ 相対比較
```

VACANが強いのは「センサーという物理データ」を持っているから。
**個人開発者は店内にカメラを置けないので、真っ向勝負は不可能。**

### ⚠️ データの落とし穴：Googleの混雑データは公式APIで取れない

多くの人が「Googleの混雑する時間帯を使えばいい」と考えるが、ここが罠。

- 混雑データはGoogleマップの**画面には出る**が、**公式のPlaces APIには含まれていない**
- 公式APIで取れるのは営業時間・住所・評価など

**なぜこれを最初に確認すべきか：**
「APIで取れるはず」と思い込んで設計を進め、実装段階で「取れない」と気づくのが
個人開発で最も時間を溶かすパターン。**データの壁は着手前に潰す。**

### 使えるデータ（実用度順）

| # | データ源 | 評価 |
|---|---|---|
| ① | **BestTime API** ★本命 | 匿名の携帯シグナルから混雑を予測。**週内ピークに対する0〜100%**で返す。無料100クレジット、以降 月$9 |
| ② | populartimes系スクレイピング | 無料だが**非推奨**。aria-labelを解析しており仕様変更で壊れる。利用は法的にグレー |
| ③ | Google Places API（公式） | 混雑データはないが、位置・営業時間・席数の手がかりは正規に取れる |
| ④ | 自前クラウドソース | ライセンス的に最もクリーン。弱点はコールドスタート問題 |

**①が本命な理由：** 「ピーク比0〜100%」という返し方が、
電車アプリの「今の電車 vs 次の電車」の相対比較そのもの。設計思想を作り直さず流用できる。

②は「学習・検証用にこっそり使うのはアリだが、公開サービスの土台にすると危険」
という位置づけ。電車アプリの「チャレンジ限定ライセンス」と同じ扱い。

## ③ ロジック案（電車アプリの資産を流用）

### 物理モデルがほぼそのまま転用できた

```
電車：ホーム滞留   ≒ 到着レート × 前列車からの経過時間
カフェ：店内滞在客 ≒ 入店レート（時間帯）× 平均滞在時間 − 退店レート
```

**カフェが混む理由の核心：** ピーク時に需要が集中し、
ヘビーユーザーほど滞在時間が長い。
つまり **「入る速さ」より「出ない（長居）」が効く。**
ここをモデルに入れると他のアプリより一段賢くなる。

### 混雑スコア式

```
混雑スコア =
  時間帯ベース係数（昼12-14時・土日が山）
  × 立地係数（オフィス街 / 学生街 / 観光地で滞在傾向が違う）
  × 天候係数（雨＝長居増、電車アプリの気象APIを流用）
  × 席数（店舗規模）の逆数
```

**LLMは数値を「言葉」に変換するだけ。計算はさせない。**
> 例：「14時の渋谷店は満席リスク高。3分歩いた○○店が狙い目」

電車アプリの鉄則 **「計算は数式、言葉はAI」** をそのまま適用。

### データの組み合わせ

```
土台（予測）  ： BestTime API → ピーク比0〜100%
補強（立地・席数）： Google Places API（公式）
天候補正      ： 気象庁API（電車アプリから流用・無料）
将来          ： ユーザー投稿で「予測のズレ」を補正（KUSEKI型を後付け）
```

3つとも「無料 or 月$9」で個人開発の範囲に収まる。

## ④ 差別化の一点

| 先行サービス | 弱点 | 隙間 |
|---|---|---|
| VACAN | センサー設置店のみ | 全店舗を"予測"でカバー |
| KUSEKI | 投稿がないと表示されない | 投稿ゼロでも統計で初期値を出す |
| Google | 判断はしてくれない | **「待つか・隣の店か」の判断を出す** |

## 教訓

- **一番の気づきは、電車という全く違うドメインで得た設計思想が
  そのまま転用できたこと。** 単発のアイデアではなく、
  自分の中に再利用可能な「型」が育ってきている証拠
- **データの壁は着手前に潰す。** 「APIで取れるはず」の思い込みが一番時間を溶かす
- **物理データで勝てない相手には、真っ向勝負しない。**
  絶対値を諦めて相対比較に振り切れば、センサーなしでも成立する
