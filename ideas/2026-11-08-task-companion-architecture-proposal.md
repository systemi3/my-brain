## 1. 何をしたかったか

Appleのリマインダーを入口に、作業の実行・中断・再開を支援する仕組みを検討する。
タスクを並べるだけでなく、本人の目的・制約・過去の知見を必要な場面で参照し、次の作業につなげたい。

MacBook Airを作業時の窓口、Mac miniを記録と知見の整理役とする構想。
GitHub連携が利用可能になったため、チャットから実際のリポジトリを確認し、今後の設計・実装を改善する流れを加える。

## 2. 何が起きたか・現時点の整理

- このチャットからGitHubへ接続し、my-brainへアクセスできることを確認した。
- GitHubへの接続と、Mac上で動くシステムの完成は別である。
- リマインダー取り込み、Mac間同期、常駐処理、AIによる作業支援は、これから設計・実装する。
- 過去の提案にある「初期実装範囲」等の表現は、今後の候補範囲として扱う。実装完了の根拠にはしない。

## 3. どう整理したか：構成案

| 担当 | 想定する役割 |
|---|---|
| MacBook Air | リマインダーの取り込み、開始・詰まり・中断・終了の記録、実行前の確認、通知 |
| Mac mini | 記録の蓄積、本人の方針・過去知見の整理、必要な判断基準の提供、翌朝の作業案の生成 |
| GitHub | 構想・設計書・コード・公開可能な知見のバージョン管理、変更案のレビュー |
| チャット上の開発支援 | リポジトリの内容を参照し、方針と実装の整合性確認、修正案・PRの作成を支援 |

チャット自体をMacの常駐実行基盤とは扱わない。
Mac側の認証・権限・起動方法・通信方法は別途設計する。

### 実行前確認の案

1. ルール確認：明確な禁止事項、必要条件、操作権限を確認する。
2. AI確認：目的・制約・過去の知見と照合し、見落としや食い違いを補足する。

AIの判断だけでルール上の禁止を解除しない。
具体的な判定条件と、人が確認する範囲は未設計。

通知は次の3段階を想定する。

| 段階 | 意味 |
|---|---|
| 提案 | 作業の選択肢や次の一手を示す |
| 注意 | 目的や制約との食い違い、確認事項を示す |
| 実行保留 | 条件が整うまで対象操作を進めない |

### 初期に検討する機能範囲

- リマインダーの取り込み。
- Airで開始・詰まり・中断・終了を記録。
- Airからminiへの重複なし同期と、失敗時の再送。
- 目的・制約に基づく注意の提示。
- 中断時や別の開発エージェント向けの引き継ぎ生成。
- 翌朝の作業案生成。

これは実装候補であり、優先順位・採用技術・達成条件は今後決める。

## 4. GitHub連携を反映した運用案

### 開発内容の受け渡し

設計・コードをリポジトリで参照し、変更はブランチ・PRでレビューできる運用を検討する。
Claude CodeとCodexで並行作業する場合は、作業ブランチを分け、同じ作業領域への同時書き込みを避ける。
実装用リポジトリは未決定。このメモの保存によって実装を開始したとは扱わない。

### 日々の記録とGitHubの役割を分ける

Airとminiの作業記録同期は、GitHubでの設計・コード管理とは分けて設計する。
同期方式、重複判定、再送、競合解決、オフライン時の挙動は未決定。

my-brainは公開リポジトリであるため、ここには公開可能な構想と整理済みの知見を残す。
生のリマインダー、日々の個人記録、非公開の判断材料、認証情報は保存しない。
それらの保存場所と、AIへ渡す情報の範囲は設計時に決める。

4. Airとminiの同期・認証・切断時の動作。
